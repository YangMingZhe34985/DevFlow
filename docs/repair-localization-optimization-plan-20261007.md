# Repair 与 Localization 优化计划

状态：五批实现及免费验收已完成，真实验收按连续三题失败规则结束。E08 完整补丁验收通过，严格端到端 0/3；Repair 稳定性目标仍未达到。新问题已记录，未继续修改冻结版本。详见[验收结果](new-dataset-validation-20261007.md)与[问题记录](new-dataset-problems-20261007.md)。

## 目标与依据

目标是让 Repair 在预算内处理真实诊断、纠正可恢复错误，并在发现新目标后完成证据交接和重新审批；让 Localization 从相关文件召回推进到公开入口、实际实现及关键行为分支的定位。

当前冻结三题严格 0/3，失败发生在 Review 之前：E09 候选准入成功，但最终重新规划 token 预检不足；E01 有候选路径和失败测试引用，却未交接实现引用；E08 遗留未使用导入，Repair 无效读取后停滞。这些问题既包含模型编辑错误，也包含宿主交接和控制逻辑缺陷。

代码检查还确认：实现导航只接受 TS/JS 文件；Localization 的有效进展要求 `parseStatus=PARSED`，非 TS/JS 的有效新源码可能不被计为进展；探索和 FINAL 切换依赖固定请求余量及粗预算。Repair 上下文重复携带诊断、源码与历史日志，准备前粗预算与最终序列化请求的预检口径不同。

阶段模型先保持现状，以便衡量系统优化收益。保留 Planner 输出契约、无工具 Review、独立评分和写入保护。全任务仍为 75 次工具、25 步、250,000 token、25 分钟；优化阶段分配和输入内容，不以扩大总上限通过验收。

## 共同设计：宿主管理证据，Agent 判断和行动

建立可复用的宿主证据记录，包含记录 ID、路径、完整 SHA、revision、实际行范围、读取来源、原文存储引用及观察完整性。诊断另存命令/profile 身份、错误码、位置、失败测试、期望/实际值和原始日志引用。任务要求、假设、未完成项与版本化源码分开。

模型可引用记录 ID，也继续兼容旧的路径/SHA/原文引用。宿主负责组装交接材料、重新验证当前身份，区分“缺失”“过期”“伪造”“不完整”。模型明确提交的错误引用仍必须反馈，不能静默换成别的证据。

Localization、Plan、Execute、Repair 共享同一证据身份和导航接口，按需提供当前视图。源码只保存一份权威原文，模型输入按用途提取；不在每条消息重复完整日志和代码。所有实际 IO 进入同一账本，缓存按 revision/路径/SHA 失效。

## 第一批：Repair 的诊断输入与证据交接

1. 将公开失败整理为宿主诊断任务：编译、类型、lint、断言、运行环境错误分别标记，保留原文引用。相同失败合并重复栈，不删除失败 ID、数值、反证或真实断言差异。
2. 优先提供当前阻断检查的错误位置、必要定义和已有补丁。小函数给出完整内容；大函数提供相关分支、必要辅助函数及未观察范围。保留最多八个当前文件的种子边界，按诊断相关性分配片段，而不是先装入长日志再截断。
3. 稳定任务中只保存诊断 ID、要求、批准范围和未完成项；源码与完整日志通过证据记录恢复。修复后的任务身份继续保留，旧 SHA 不能再授权编辑。
4. 范围交接由宿主查找当前已观察实现证据和失败测试证据。模型遗漏实现引文但宿主已有完整、当前且相关的记录时，可以直接组装只读调查包；无需模型再次抄写。宿主只有文件内容、尚未选定相关区域时，使用有界读取补齐候选区域，明确其关联只是待核实假设。
5. 缺失必要证据时返回具体待补项；需要模型选择区域或解释关联时，回到同一 Repair 的有限纠正决策。不能将路径存在当根因证明或写入授权。过期、伪造引用单独反馈并保持阻断。
6. 使用共享清单和版本缓存构造 Repair 输入，去除每次 Repair 重新递归列目录的准备路径。

验收：回放 E01 当前答复，宿主已有证据足够时能够构造合法调查包；确实缺证时明确返回待补内容。合成伪造、过期和无关联候选继续被正确处理。E08 的 F401 诊断进入首个 Repair 请求，两个导入位置及当前 SHA 可直接用于合法编辑。所有读取仍不授予新写权限。

## 第二批：Repair 的有限纠错与统一预算

1. 让宿主分别记录实际修改、有效新证据、可纠正协议错误、重复无进展、权限拒绝。修正参数不算进展，但首次可纠正错误可以消耗一次已有纠正机会，不立即被第二次无进展吞掉。
2. `readEvidenceArtifact` 的两个行号均省略时，允许宿主返回明确标注的有界首段；仅缺一个边界、非法范围或错误 section 则反馈具体字段及合法调用示例。默认读取不得越过现有片段/原文上限。
3. 工具参数、交接格式、编辑格式和 LENGTH 恢复共用该次 Repair 的一次纠正额度。额度在请求前预占并持久化，重启不重置；重复相同错误或再次截断明确停止。纠正动作受限于报错内容，不能借纠正重新开启任意探索。
4. 把重新规划、原范围修复、证据答复作为宿主的执行分支。确认需要新范围后及时结束旧范围探索，准备只读重新规划；普通 lint/编译修复优先在原范围闭环。
5. 统一请求构造与预算估算入口。当前请求使用实际序列化输入、工具定义和配置输出上限；尚未构造的下游请求采用显式保守估计，构造后重新核对，分别记录估计值与实际值。
6. 按实际分支预留编辑、现有纠正、收尾、公开验证和 Review；重新规划分支另外预留 Planner 与批准后的 Repair。互斥分支不叠加预留，同一恢复不被多层重复预留。预留只转移、消费或释放，不作为已用 token 重复记账。
7. 首个 Repair 请求以约 8–12k 输入 token 为压缩软目标，优先静态去重与按诊断裁剪。必要证据超过目标时允许预算内扩展或明确停机，不能静默丢弃关键记录。完整历史留在宿主，不新增 LLM 摘要阶段。
8. 保留候选及未完成诊断；预算、权限、缺证、停滞分别报告。最终 Planner 预检因预算失败时使用预算归因，避免被包装成提案质量/证据失败。

验收：E08 的缺省范围读取或一次参数纠正后能继续处理 lint；连续错误、越权、过期 SHA 和预算不足仍停止。E09 回放从相同 250k 总额出发，统一估算与最终实际请求一致；重复日志显著减少，足以构造重新规划时确实到达模型调用边界，不足时在可选探索前给出具体缺口。测试覆盖额度持久化、末步纠正、缓存命中和互斥分支预留。

## 第三批：Localization 的探索控制与证据保留

1. 将检索结果区分为公开入口、包装/转发、实际定义、测试/复现及配置。命中包装层后继续寻找被调用实现；函数体截断在关键分支前时，将它登记为优先补读缺口。
2. 进展判定不再要求 TS/JS 的 `PARSED` 标记。SHA 已验证的新相关源码范围、可信定义、关系或反证可以构成进展；仅改变搜索词、重复区间、缓存元数据和重复假设不算进展。语法解析质量与调查进展分开记录。
3. 根据剩余预算、实际进展和真实 FINAL 请求预留决定探索与收尾。初期保留当前模型调用硬上限，通过压缩重复目录/证据和更准确的预留改善探索机会。只有完成成本对照后才考虑重新分配阶段预算，总任务上限保持。
4. 最终请求还出现探索意图时，明确记录未完成的具体读取任务及其来源；有可用探索额度时先执行再总结，确实不足时把缺口交给后续阶段。不能把未读取的候选当已观察实现。
5. 保留候选多样性、入口证据、关键分支和反证；按照行为相关性淘汰冗余条目，避免整个目录重复命中挤掉一个关键实现。
6. 交接保持简短：主候选、已观察实现、公共入口/测试关联、尚缺证据和版本引用。状态区分“相关文件已找到”“实现已观察”“根因待核实”，不用主观高置信度替代证据，也不增加 Planner 必填字段或新的合法性门槛。

验收：新增 Python/Java/C++ 相关源码可以被计为进展；重复片段不能。E08 包装层不能作为已经确认的真实实现收尾；E01 的搜索实现候选及缺失分支不能在交接中无提示消失。预算不足的 FINAL 明确返回缺口；正常总结、格式恢复仍有预留。

## 第四批：共享的多语言实现导航

逐个语言适配器交付并验收，再扩展下一种语言，避免一次建设完整语义图。

1. 通用层提供定义、导入、局部调用点和源码单元读取。输出携带语言、解析方式、完整性、关系来源和歧义候选。读取绕不开路径安全、文件大小、SHA 和全局 IO 预算。
2. Python 优先支持模块/相对导入、别名、类方法定义及简单直接调用。通过只解析源码的方式建立关系，不 import 或运行被测仓库代码。动态注册、反射及运行时装饰器关系保留 UNKNOWN。
3. Java 支持包名、import、类/方法声明、接收者可静态确认的调用点。接口实现、重载和依赖注入保留候选集合；不能将同名方法连成确定调用边。
4. C++ 支持头文件/实现配对、命名空间、定义位置及可确认的直接调用；模板、宏、条件编译及虚调用不完整时明确降级。仅词法匹配标记为候选关系，不宣称语义调用图完整。
5. 从公开 API/复现和候选两端建立有界局部关系图，优先读取实际影响结果的分支。发现只有转发内容、同名符号歧义或重复无进展时换分支或做定向搜索。图不完整仍可图外读取。
6. 同一导航能力供 Localization、Planner 补查和 Repair 使用。宿主向 Planner 保留相关而尚未批准的实现引用，但不会把所有候选自动变为可写范围。

验收：Python 的包装/真实实现同名案例、Java 事件监听器到缓存调用、C++ 头文件到搜索实现分别回放；增加改名、移动目录、同名诱饵、缺失依赖、循环导入和旧 SHA 样例。报告真实目标召回、关系误连率、关键分支覆盖和成本；不能只看图节点变多。现有 TS/JS 导出别名、barrel、循环与失效测试必须保持通过。

## 第五批：集成验收与真实实验

每批保存独立代码身份、免费回放、相关回归及必要 Docker 结果，通过后才进入下一批。完整工程检查覆盖 lint、typecheck、全部默认测试、格式和公开文件检查。

先做受控阶段验收：E09 的公开候选用于 Repair/重新规划预算与交接；E01 用于“模型遗漏引用但宿主有当前证据”；E08 用于 lint 修复、参数纠正和真实实现导航。若调用真实模型，阶段回放与完整流程结果分开报告；候选只能来自公开历史观察，不注入私有评分或标准答案。

随后冻结代码、模型、输入、公开 profile 和评分器，运行 E09 → E01 → E08 → E03 → E04，每题一次完整流程，连续三题严格失败即停止。不预设成功率，未运行项标为未验收。E02/E06/E07/E05/E10 继续保留为后续数据，不在开发过程中反复调参；在已知路径稳定后再单独安排验证。

| 维度         | 必须报告的指标                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------- |
| Localization | 文件/函数或代码区域召回、公开入口到实现覆盖、同名误选、未知关系比例、有效新证据/物理读取、进入 FINAL 的具体原因 |
| Repair       | 原范围诊断修复率、首次错误纠正结果、无效调用/重复读取、范围交接缺项、停滞/预算停止、每次实际修改消耗的 token    |
| 重新规划     | 候选准入、实际 Planner 请求、新审批、候选恢复、批准后实际修改，逐项分开                                         |
| 最终效果     | 公开 build/typecheck/lint/test、独立 Issue/原测试/完整性、Review、严格结果、耗时与总成本                        |

验收追求端到端有效修复和明确的阻断原因，不以减少拒绝、增加候选或多跑几轮作为成功。首次集成用原阶段模型建立对照；模型升级仅在后续独立对照中评估，避免掩盖工程改进或引入归因混淆。

## 兼容、权限与预算

新增证据记录、诊断任务、语言能力、恢复状态和预算预留信息均为可选字段，旧任务/报告/checkpoint 可读。必要的旧数据缺口显式标 UNKNOWN，不能伪造来源或清零已消费额度。以共享组件和阶段策略逐步替换旧实现，验收后删除废弃路径；不长期维护多套 Planner/Execute/Repair 实现。

Repair 继续直接修改已批准文件；读取新候选不授予写权限。扩大范围仍须一次只读重新规划、新 PLAN 审批及版本化候选恢复；保留最多两次 Planner 请求和全流程一次范围重新规划限制。公开验证和独立 Review 仍必需，未通过的真实诊断不能被证据答复覆盖。
