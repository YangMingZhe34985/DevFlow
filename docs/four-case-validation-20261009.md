## 失败归因与保留问题

### E05：候选行为不完整，超时及后续准入阻断

候选解决了 Issue 复现，但公开测试 `invalidates only the changed environment variant` 仍失败：实际失效条目数 2，期望 1，环境变体隔离未满足。必须继续修复，不能凭 Issue PASS 交付。

同 Session 在测试反馈后补读相关实现。随后一次 Coding HTTP 在约 60 秒处超时，没有 usage 回执；重试决策被 Scheduler 在派发前拒绝。准入时剩余 token **109,516**，本次请求及必要后续路径报价 **135,875**，缺口 **26,359**，`requestIssued=false`。实际已确认 token 112,575，不能描述为实际消耗达到 250,000。

超时请求仍保留原 **¥0.768104** 全额费用预留，Run 原 ADMITTED 记录保留，没有伪造结算或缩减消费。应后续审计请求期限、未知请求预留及后续路径估算；仅凭本批数据不能认定全部预留冗余，也不直接提高硬限。

### E06：跨层证据仍不完整

初始 Planner 和一次只读调查未共同得到决定性实现。调查中发生一次 LENGTH，既有恢复成功输出完整 UNKNOWN，仍明确缺少：

- 正常 close/reopen 的 load、segment discovery 和 lookup 重建实现；
- compaction 输出／commit 的落盘及注册路径；
- 相关公开测试及持久化／manifest 行为证据。

实际看到的 rotate、输入规划及内存缓存片段不足以推断持久化修复。最终全部候选仅 INSPECT，没有修改，不应強制转成 EDIT。后续应审计 C++ 方法／消费者导航及请求联合可见性；本批不能归因为“实现证据已充分但模型判断错误”。

### E10：范围闭环恢复，但跨视图修复及下一轮工具预留仍不足

初始批准范围是 summary builder 和 event projection；候选未通过公开测试。有效范围冲突真实进入 Planner，新 PLAN 审批覆盖保留的 summary 修改及新增 event codec，原 Session 和候选恢复后继续写入。

第二版候选使公开失败数由 32 降至 22，但仍有状态持久化、SKIPPED／COMPLETED 区分、reload、bundle／summary／API 一致性问题。不能把局部失败减少或两个源码修改当作 Issue 已修复。

再次失败后，后续 Repair 准备在拟进行下一项工具操作时被阻断：**已消费 75，拟观察 76，硬上限 75**。记录为 `REPAIR exceeded the toolCalls execution budget`，没有第 76 次实际消费或新的付费请求。该次资源尚有 token 和时间余量，直接瓶颈是逻辑工具预算。

后续优先审计宿主准备／恢复／必要诊断补读的实际操作成本，以及继续修复路径是否在前一决策中预留完整；再核查 Planner 的消费者覆盖。重新规划已派发，本批问题不能继续写成“Replan 从未发出”。Review 尚未运行，不能归因为 Review 误拒。
