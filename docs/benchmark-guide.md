# DevFlow 验证与评测使用说明

本文件保存可重复使用的操作与判分规则。历史成绩集中在[溯源书第11节](devflow-history-and-architecture.md)，不再为每次实验重复一套架构说明。

## 1. 日常工程验证

在配置好依赖的仓库根目录运行：

```bash
npm run check
npm run build
npm run format:check
npm run db:validate
node scripts/check-release-files.mjs
```

`check` 包含 lint/typecheck/默认测试。环境门控集成可能 SKIP，不能把跳过当成通过。纯文档修改应优先检查格式、链接、公开文件及版本/来源准确性，不以重复付费实验验收文档。

默认单元测试使用 Fake Model/本地模拟，不能证明真实模型会正确定位或修复。常规验证命令不会因为使用 Fake Model 就取消真实工具/数据库边界；是否使用 Docker、数据库和外部模型以相应测试开关为准。

## 2. Docker、数据库与浏览器

启动基础设施和构建沙箱的入口在根 README。以下脚本复用现有验证设施：

| 入口                                               | 验证范围                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------- |
| `npm run test:p3`                                  | 沙箱读写/命令、隔离与生命周期。                                       |
| `npm run test:p9`                                  | 生产审批工作流及 Web/SSE 交接。                                       |
| `npm run test:p10`                                 | 经批准的 GitHub 发布、幂等及恢复模拟。                                |
| `node scripts/run-resource-budget-integration.mjs` | 临时 PostgreSQL、预算/团队/租约、生产 Coding 与公开诊断 Docker 集成。 |
| `npm run test:e2e`                                 | 浏览器端工程路径；查看 tests README 的前置条件。                      |

脚本使用独立测试库和归属明确的资源；清理只处理自己创建的库、队列和容器。不要为了恢复环境删除开发数据库或其他项目容器。公开文件检查针对实际 Git 候选树，配置密钥、个人路径、原始数据和账本不得提交。

历史 P11 45 秒夹具与后来 Planner 请求期限存在不兼容记录；执行相应脚本时按实际结果报告，不能沿用早期“全部通过”的结论。完整测试说明见 [tests/README.md](../tests/README.md)。

## 3. 严格成功的判定

一次真实 Issue 的严格 PASS 同时要求：输入/冻结身份与完整轨迹有效、实际合法补丁、完整配置的公开验证通过、独立 Issue/原测试/完整性通过，以及独立 Review 完成批准。具体项目另有必需评分项时一并满足。

以下情况保持失败或未完成：只有 JSON Plan、全 INSPECT 未进入编辑、只有空 diff、仅基准原测试通过、Review 未运行、候选独立通过但工作流停止、补丁通过 Test/Review 而 Issue-specific acceptance 失败。NOT_RUN 不填成 PASS；未知用量不填0；空候选失败不自动解释为引入回归。

Review 通过是模型裁决，公开检查是可复现命令结果，独立评分是隔离的任务验收，三者都需要单列。私有评分器、参考补丁或正确文件标签不反馈给模型，不加入 public verification profile。

## 4. 每个真实批次应冻结什么

记录源码提交/Runtime digest、公开输入与基准、模型绑定和推理参数、输出/上下文额度、executionMode/localizationMode、验证 profile、依赖镜像、评分身份、Run 硬限及费用分配。新审批和恢复沿用本次 Run 的已用消费和绝对期限。

正常批次期间不修改实现、不自动重试。若用户授权迭代：先结束原批、保存原始失败，免费重现已证实缺陷，通过修复回归后形成新冻结批次；新成功不能覆盖旧失败。最多尝试次数是上限，缺少新的修复依据时不盲目耗尽。

同预算的 single/workflow/team 对照还需保持模型、PRG 模式、工具策略、输入、评分、冷缓存和执行环境一致，区别只在求解组织。不同仓库/难度/停止规则不能直接比较成功率；热缓存收益应另测。多个 Worker 的独立 Run 并发，与同 Run 多 Agent 或同库租约竞争是不同测试。

## 5. 指标与成本

至少单列：模型决策尝试、实际 HTTP、input/output/reasoning Token、逻辑工具、内部执行、可观测物理 IO、墙钟/活动耗时、调用延迟、候选修改/测试/Review/Replan、严格结果及主因。

上下文需要记录最终序列化 body/guard、Schema、估算 Token、指纹、实际展示源码范围、省略原因、反证保留和摘要是否真正派发。累计输入很大并不意味着某次请求超过上下文窗口；多轮重复输入会累计计费。请求变短也不意味着定位或修复质量提高。

AgentMessage 数量不等同协作质量。要证明通信，需要发送者、接收者、证据身份、接收记录和可核查的后续决策变化。受控模型可验证工程链路，真实模型仍需独立实验。

同时记录实际费用、保守预约和未知上界，区分 Worker Scheduler 与实验控制器拒绝。缺少下一题最低授权预留时停止；新的 Run/Agent/Replan 不能绕过累计费用边界。依赖平台与实际 usage 的实验不能只用本地估算伪造账单。

## 6. 数据和公开仓库

普通工程夹具位于 tests；可信真实数据与控制器需要另行配置。干净公共 checkout 不包含所有本地私有评测资产，因此不能承诺直接复现个人已运行的数据集。

原始模型请求、回复、候选、账本、评分明细和冻结证明留在忽略目录。公开报告只保留必要结果、身份和归因；删除重复报告后仍保留原始产物及可恢复快照。
