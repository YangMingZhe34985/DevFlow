# DevFlow 验证与评测使用说明

本文件保存可重复使用的操作和判分规则。历次成绩记录在 [v4 进度](v4/PROGRESS.md)。

## 1. 日常工程验证

在仓库根目录运行：

```bash
npm run check
npm run build
npm run format:check
npm run db:validate
node scripts/check-release-files.mjs
```

- `check` 包含 lint、类型检查和默认测试。
- 依赖环境开关的集成测试会显示 SKIP，**跳过不等于通过**。
- 单元测试使用 Fake Model，不能证明真实模型能够正确修复。

## 2. Docker、数据库与浏览器

| 入口                    | 验证范围                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| `npm run test:p1`       | autonomous 执行器在真实 Docker 沙箱中的求解、验证、审查、检查点和多次尝试（Fake Model）。 |
| `npm run test:p3`       | 沙箱读写、命令、隔离与生命周期。                                                          |
| `npm run test:p5`       | API → BullMQ → Worker → autonomous/Docker → PostgreSQL，以及排队、重试、取消和租约恢复。  |
| `npm run test:p9`       | 在浏览器中创建 autonomous Run，查看审查结论和 Diff；另含无改动时失败的情况。              |
| `npm run test:p10`      | 经批准的 GitHub 发布、幂等与恢复。                                                        |
| `npm run test:postgres` | 临时 PostgreSQL 上的 Run 所有权与租约，以及经由 RunProcessor 的 autonomous 执行。         |
| `npm run test:e2e`      | 浏览器端界面路径，前置条件见 tests README。                                               |

这些脚本使用独立的测试库，以及归属明确的队列和容器，清理时只处理自己创建的对象。**不要为了恢复环境而删除开发数据库或其他项目的容器。**

## 3. 真实模型评测

两套评测都在 `scripts/v4/` 中，**需要用户批准预算后才能运行**。

| 评测集                        | 入口                                  | 数据位置                                                    |
| ----------------------------- | ------------------------------------- | ----------------------------------------------------------- |
| 合成回归集 E01–E10            | `scripts/v4/phase0-dataset.ts`        | `datasets/`、`.devflow/dataset-suite/`                      |
| 外部留出集（SWE-bench 20 题） | `scripts/v4/external-set/evaluate.ts` | `.devflow/external-set-suite/`，构建方法见该目录下的 README |

外部集的 `--live` 必须同时给出 `--cases`、`--budget-cny`、`--per-case-cny`，缺一项就拒绝运行。

求解设置默认与合成集评测程序一致：reasoning low，输出上限 8192。

## 4. 严格成功的判定

一题严格通过，必须同时满足：

- 输入和冻结身份有效；
- 有实际的合法补丁；
- 公开检查通过；
- 独立的官方评分通过；
- 评分期间没有修改受保护路径。

以下情况都算失败或未完成：

- 空补丁；
- 只有原有测试通过；
- 评分没有运行。

另外：

- NOT_RUN 不能记为 PASS，未知用量不能记为 0；
- 审查结论（模型判断）、公开检查（可复现的命令结果）和官方评分（隔离的验收）要分别记录；
- 私有测试、参考补丁和评分材料不得进入求解或审查容器。

## 5. 每个批次应冻结什么

记录以下内容：

- 源码提交；
- 数据集和镜像的 digest；
- 模型绑定和推理参数；
- 输出和上下文额度；
- 公开检查 profile；
- 评分身份；
- 每题的费用上限和批次预算。

批次进行期间不修改实现，也不因为模型失败而重跑。如果评测入口本身出现缺陷，先停止批次并保留原始失败记录，修复后再开新批次；新的成功不能覆盖旧的失败。

## 6. 指标与成本

**至少要单独记录以下指标：**

- 模型调用次数；
- Token：输入、缓存命中、输出、推理；
- 工具调用次数；
- 耗时；
- 费用：已结算、审查、未确认；
- 尝试与修订次数；
- 审查结论；
- 停止原因；
- 官方结果。

**费用口径：**

- 同时记录实际费用、保守预约和未确认上界；
- 下一题的最低预约放不下时就停止；
- 不得用本地估算冒充供应商账单。

## 7. 数据与公开仓库

原始模型请求和回复、候选补丁、费用账本、评分明细和冻结证明，都保存在被 Git 忽略的目录中。公开报告只保留必要的结果、身份信息和归因。本地数据集的清单见 `.devflow/DATASETS.md`。
