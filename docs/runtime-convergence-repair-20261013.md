## 修复一：按模型与输入/输出计价

- 初始 Planner 在请求边界重新计算当前证据对应的 Coding/Review 投影，不继续使用团队调查之前的旧证据估算。
- Replan 使用准备阶段已生成的操作计划，保留一次 Coding 恢复、Review 及其可用恢复预算。
- Planner 的一次输出恢复单独按当前 Planner 绑定报价；Review 恢复也按自身绑定计价。恢复 token 已包含在总预留中，不再次累加。

## 修复二：精确编辑失败使用现有一次纠正信用

E04 原失败不是工具错误写入，而是 LF 参数与 CRLF 源码不匹配，随后第二次无进展直接停机。

`replaceText` 现在对可证明的均一换行差异提供 `textFailure`：具体字段、路径、完整 SHA、无需补读标记。只有标准化后恰好唯一匹配，才给出该结构；宿主不会自动转换模型参数。

Runtime 还必须核实 mutation 观察完整、源码未变、revision 未变、输入 SHA 与当前完整 SHA 一致，才允许消耗原有的一次编辑/格式/截断共享纠正信用。模型必须显式提交 `MATCH_FILE`。无效调用仍累计无进展；纠正机会不算新证据、不重置计数、不开放搜索、不扩展审批。

过期 SHA、未知/部分 mutation 观察、真实源码变化、已使用信用仍拒绝此快捷纠正。其他任意 `CONFLICT` 不会被一概接受。默认 EXACT、混合换行拒绝、字面转义、重复匹配和写入 CAS 保护保留。

## 修复三：收尾限制不能阻断宿主的必要校验

E05 的冻结调用证实，模型调用 `finishPhase` 后，Runtime 为恢复候选插入的 `gitDiff` 被 `HOST_AUTHORIZATION_HANDOFF` 拒绝。随后控制器又把这个宿主调用当成模型请求了额外工具，返回 `AUTHORIZATION_HANDOFF_UNRESOLVED`。

现在只有 Runtime 自己生成并登记的当前 diff 校验 ID 可以穿过 finish-only 限制。它仍经过工具预算、原授权、Sandbox、完整 diff/源码身份及实际消费检查。模型请求的其他读取、编辑或自行调用的 gitDiff 仍拒绝。控制器根据原模型工具列表判断是否违反 finish-only，宿主插入项不再混入该判断。

有效 `finishPhase` 后仍立即交给外部验证，不追加确认轮次。合法补丁本身仍不等于模型已经结束；连续无进展、写入失败和未完成目标保护继续保留。

第三批提交：`eb2a589`。定向收尾、Session 和工具恢复回归通过。

E05 Docker 回放加载原始 821 字节候选、原保存会话及最后一次 finish 参数，并核对当前源码 SHA。在冻结期限内的模拟时钟下重放终止前决策：一次受控模型决策、两次工具计数，候选可提交，源码未再次修改，消费、信用和期限连续。只在回放器中移除终止结果以重现失败前边界，生产恢复不会重新执行已完成阶段。本次没有重新跑 E05 的完整 Test/Review，因此不记为新的严格成功。
