# Resource Budget Scheduler：开发验收与实验对照

本轮完成 Worker 资源调度器接入，真实 E10 已越过旧的 Replan 工具预算预检，完成 Planner 派发、新审批和 Coding Session 恢复。但恢复后的工具策略仍阻断编辑，E10 没有产生补丁。**v2.4 的真实验收目标未达成，包版本保留 2.3.0。**

冻结批次四题各运行一次，严格通过 **1/4（E07）**。这不能证明整体修复成功率提高；E02 本轮回归失败，E08 仍停在 Review 证据缺口。冻结期间没有根据结果修改生产代码、放宽评分或重跑完整流程。

## 版本保护与实现

- 基线：`b749eef`，v2.3；备份分支 `codex/pre-resource-scheduler-20261008`。
- 开发分支：`codex/resource-budget-scheduler`，主分支和备份保留原版本。
- `54a698c`：Scheduler、持久账本、数据库 CAS 与预算不变量验收。
- `1953b64`：接入实际模型/工具请求、公开验证、源码缓存、重新规划操作清单及恢复计量。
- `e580108`：架构与配置文档，也是四题真实实验的冻结提交。
- `6706a02`：实验后修正本轮发现的“明确未派发仍保留费用预留”缺陷；该修正只有免费验收，不覆盖本批真实结果。

架构见 [Resource Budget Scheduler](resource-budget-scheduler.md)。调度器提供 `quote / reserve / admit / settle`，将 Hard Limits、操作清单估算和实际消费分开。顺序操作累计成本，只有显式互斥分支使用共享成本加分支最大值。预留不作为消费，缓存命中不作为物理读取。

保持原有 **75 次逻辑工具调用、25 步、250,000 token、25 分钟**上限，以及原修复次数、审批、测试保护、Sandbox、统一 Coding Session 和独立 Review。没有为 E10 添加生产特例。

## E10：预算阻断解除，恢复后的旧缺陷仍在

真实顺序为：Coding 发现原范围外的持久化目标 → 公开失败核实 → 一次 Replan → 第二份 PLAN 批准 → 同一 Coding Session 恢复。必要预留为 **27 次逻辑调用 / 31 次内部执行**，当时剩余 58 次逻辑调用；准备实际读取 6 次，复用源码缓存 7 次、元数据缓存 11 次。

恢复后，模型按 `readFile` 工具 schema 的 200,000 字节默认值请求源码；宿主此时却执行隐藏的收尾刷新上限 16,384 字节。该参数问题被归类为 `HOST_AUTHORIZATION`，将下一次请求限定为 `finishPhase`。模型缩小到 16,384 后仍被拒绝，最终 `AUTHORIZATION_HANDOFF_UNRESOLVED / AGENT_STALLED`。请求中还保留旧的独立权限交接提示。

停止时仍有 84,654 token、34 次逻辑调用和 13 步余额，**不是硬预算耗尽**。对照 `b749eef`，上述读取上限、权限错误转收尾和旧提示保留逻辑已经存在；本轮没有修改这些规则。调度器影响探索关闭时点，但本次直接阻断属于越过旧预算问题后暴露的既存动态工具契约/交接缺陷。

## E02：上下文不足与新增记账缺陷分开处理

首次补丁未通过公开测试，诊断回到同一 Coding Session。Replan 核实读取 4 次，命中源码缓存 8 次、元数据缓存 15 次；新审批和恢复完成，并保留原候选的实际变化。

后续 Coding 的完整输入为 **98,090 字节**，超过适配器原有 **96,000 字节**限制，返回 `requestIssued=false`。该字节预检在 v2.3 已存在；本批没有继续执行模型请求，没有把上下文裁剪问题伪装为模型错误。

新 Runtime 的异常处理却把所有 `model.generate` 失败都当成未知派发，错误保留 **40,876 token / 490,848 costMicros**。这是本轮新增缺陷，不能用审计 PASS 掩盖。实验后的修正使用明确的宿主未派发证明结算零 token/费用，保留本地调用尝试和耗时；一般传输失败仍保留未知占用。

该 Run 另有一条 800 字节源码读取缺少可靠完成记录，不能连带假定为未执行或释放。历史账本和本批结果保持原样；后续需要完善 IO 结果回执和对账诊断。

## E08：补丁验收通过，审查仍不完整

公开四项检查及独立三组验收全部通过，但 Review 连续三次返回 `NEEDS_EVIDENCE`，尚未取得 CLI 调用及成功执行历史记录路径的必要证据。独立验收通过没有替代 Review 的判断，因此严格结果为失败。

最后一次 Review 于 14:05:06 UTC 结束，`RUN_FAILED` 于 14:09:34 UTC 持久化，末端间隔 **268.071 秒**。运行共记录 838 次内部执行、823 次 IO 读取。此阶段的候选取证、源码收集和账本持久化开销应进一步分解；单凭新旧统计口径差异不能断言性能退化。兼容 `durationMs` 未包含全部终结耗时，也不能作为完整端到端墙钟时间。

### 预算报价与真实 IO 改善

旧 E10 状态的逻辑预留为 40、余额为 38，准备尚未读取就停止。相同历史状态的免费报价改为 32 次逻辑调用、34 次必要内部执行；可选 Review 读取全部加入时为 40 次内部执行。差异含有计量口径纠正，**不等于节省八次物理 IO**。

这份报价以一个实际修改文件、六个准备路径、八个诊断文件和四条已提供的公开检查为前提，不假设缓存命中，也不保证任意新增范围都能容纳。真实 E10 的 27/31 报价来自零修改候选和不同准备状态，不能与历史 32/34 混写。

实际减少 IO 的回归证据：在 HEAD 已核实并可缓存的前提下，修改/新增/删除三文件首次检查点需要 7 次操作（未缓存 HEAD 时还需一次核实），随后身份计算无需读取；同身份重复保存只做一次 status，免去六次重复源码读取。新 Sandbox 恢复仍执行 11 次必要校验、写入和复核。两文件缓存中仅 a 发生实际变化时，只重新读取 a，不重读 b。

## 审计边界与后续优先级

冻结身份、完整公开 profile、保护与费用审计通过。私有审计加载器遗漏了 `expectedProfiles` 初始化，最终使用独立副本补齐读取冻结 profile 的代码并封存修正 provenance；原冻结控制器、评分器和实验结果没有改动。该审计允许失败任务保留未知预留，未自动发现 E02 的“已知未派发”分类错误，所以额外人工审计结论必须保留。

账本保证固定 operation ID 的原子、幂等结算，不保证外部 HTTP 与检查点的 exactly-once 事务。初始快照、仓库初始化和 Sandbox 创建的底层 IO 尚未逐项接入；价格/币种身份由实验另行冻结。未知费用不会自动对账或释放。这些限制见[架构说明](resource-budget-scheduler.md)。

下一步应优先处理：

1. **恢复后的动态工具契约与控制提示**：公开实际读取限制，区分可纠正参数与权限拒绝，新审批后消除失效控制提示，保留预算/尝试次数及写入保护。
2. **恢复请求的真实上下文投影**：在完整 Provider 输入检查前保留任务、当前源码和反证，删除失效/重复控制历史；不提高原上下文或硬上限。
3. **IO 回执与终结开销**：定位未完成读取及大量候选取证/账本操作，按实际耗时和版本身份减少重复工作。
4. **Review 证据导航**：补齐跨语言调用与消费者证据，继续区分审查未完成、确认缺陷和补丁独立验收。

本轮没有完成 E10 严格修复，也没有通过全部成功回归，因此不升级、不发布 v2.4.0。原始请求、源码候选、账本、评分材料和私有审计记录继续排除在 Git 外。
