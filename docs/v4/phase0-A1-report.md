# Phase 0 A1 报告：最小自主 Agent 与旧系统同条件对照

运行日期为 2026-10-14，运行代码为 `a572b2e`。原始材料（轨迹、补丁、评分）位于 `.devflow/v4-phase0/A1-live-20261014-r2/`，该目录不入库。

## 1. 结论

- 一个只有 `bash` / `read_file` / `edit_file` / `submit` 四个工具、主循环约 300 行的自主 Agent，在 E01–E10 上各跑 1 次，**严格通过 9/10**。
- 同一批题目上，旧系统 2026-10-13 的三个批次分别是 5/10、3/10，以及失败五题定向复测 1/8。
- 旧系统在这 28 次运行中**从未通过的 E01、E08、E10，这次全部通过**。
- 唯一失败的 E06 已在第 31 轮准确说出根因，随后触发了按无缓存全价计算的 ¥4 上限；它 93% 的输入是缓存命中。

这满足了方案 Phase 0 的决策条件：对照 Agent 不低于现系统。**v4 方向得到直接支持，建议进入 Phase 1。**

### 旧系统长期失败的三题

- **E01**：在第 5–6 轮定位到 `prepareRemoval` 只提交变空的倒排表，修改两处后提交。
- **E08**：用 `rg` 直接找到 `PluginRegistry.lookup_execution`，第 12 轮通过。旧系统的三个 Investigator 当时用自然语言检索，始终没有找到这个函数。
- **E10**：先运行测试看到 33 个失败，再逐一修复全部 4 个注入文件，其中包括旧系统只看到无关 5 行的 `event-codec.ts`。

### E06 的失败过程

Agent 先自行编写了 C++ 复现程序，并对 MANIFEST 和 segment 文件做了十六进制检查。到第 31 轮，它给出了正确根因：`applyReplayed` 按 segment id 判断是否回放，而压缩输出的 id 大于活动 segment。下一轮的最坏情况成本会超过 ¥4，于是停止。

如果按缓存价计费（见第 5 节的估算），本题实际花费约 ¥1，在同一上限内还能继续修复。

## 5. 必须说明的限制

1. **每题只跑了 1 次**。10 题样本中 1 题就是 10 个百分点，需要重复运行来估计方差。
2. **没有独立 Review**。旧系统的严格判定还要求 Review 批准。若只按评分器计算，旧系统 failed-five 批次会从 1/8 变为 2/8（E01 r2 补丁已全部通过，只是 Review 没有派发），结论不变。
3. **合成数据集可能被识破**。E10 的提交摘要写着 “planted corruptions”，说明注入的回归有时能被识别为人为破坏。两边看到的输入相同，所以对比本身是公平的；但 **E01–E10 的绝对通过率很可能高估了真实 GitHub Issue 上的表现**，需要外部真实 Issue 留出集（Phase 0.5）来校准。
4. **费用按无缓存上限价计算**。百炼会返回 `cached_tokens`，但这批运行没有确认缓存折扣价。若缓存命中按输入价的 20% 计费（**未经核实**），本批实际费用约 ¥4.3，而不是 ¥14.22。请以百炼账单为准。
5. **第一次启动中止过**。A1 第一次启动时，`edit_file` 把 `/workspace/...` 绝对路径误判为受保护路径，花费 ¥0.67 后立即中止，修复（`a572b2e`）后重跑。中止前的轨迹保留在 `A1-live-20261014-aborted-pathbug/`。A1 总花费为 ¥14.89 / ¥40。

## 6. 对 v4 的影响

- **方向得到验证**：通用工具、能自行运行测试、全仓可写、追加式上下文，这四点组合起来，比多层宿主管控加多 Agent 协作有效得多，而且更便宜。
- **预算应改为缓存感知**：E06 是唯一的失败，它的根因就是计费口径。RunMeter 应按实际缓存价结算（0.1 已经支持，只差确认百炼的缓存单价）。
- **Phase 1 的重点**：把 Kernel 变成产品主路径（Orchestrator、持久化与恢复、事件流、diff 级审批、独立验证与 Review），而不是继续增加 Agent 内部机制。
- **后续待测**：重复运行估计方差、外部真实 Issue 留出集、reasoning low 与 high 的对比、缓存感知预算下 E06 的表现。
