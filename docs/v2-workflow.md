# DevFlow 2.0 workflow

The Worker runs one production proposal Planner and one tool-calling execution runtime. Historical grounded/iterative Planner implementations and experiment runners are excluded from the public tree. Compatibility schemas and execution guards remain for existing persisted approvals; they are not alternative production agents.

```text
Immutable repository + Issue
  -> bounded retrieval / Localization
  -> Planner proposal
  -> human approval
  -> Execute -> deterministic Test
                  -> targeted Repair -> Test
  -> independent Review
       -> targeted Repair / evidence response -> Test -> Review
  -> diff artifact -> optional approved GitHub delivery
```

Planner's proposal contains `decision`, `goal`, `approach`, `candidateFiles`, `verification` and `uncertainties`. Exact symbols and evidence IDs are optional hints. `EDIT` proposes a source repair target; `INSPECT` is read-only supporting evidence. Missing modification paths trigger investigation; intentional new files require `operation: CREATE`. Empty or all-inspection proposals permit only bounded investigation. The host constructs approval scope from verified source identity; candidate suggestions never grant permission.

Protected edits are excluded from write scope. A protected test suggestion alongside a viable source direction can continue as read-only investigation. A solution depending entirely on prohibited edits stops with a scope conflict. Execute and Repair verify the approved path and current full-file SHA before edits; whole-file writes also require complete observed content. Historical artifacts cannot authorize current writes.

Localization builds a versioned, bounded TS/JS static dependency/export artifact. Retrieval separates file paths, public API names and reproduction-local variables, prioritizes relevant implementation/version paths and retains tests as navigation evidence. A partial content index can run bounded, query-directed source searches. Localization and Planner discovery share symbol navigation through actual imports, export aliases and helper definitions. The host hands observed implementation windows, complete source hashes, revision and missing evidence to Planner independently of model-selected candidates. These observations do not add proposal schema requirements.

Execute and Repair can request `queryRelations` with paths and optional symbols; symbol queries also return bounded current implementation windows from the same navigator. The model chooses whether to call it. Current overlays invalidate changed relationships; incomplete graphs allow ordinary public source reads. Navigation never expands write scope or satisfies the complete-read requirement for whole-file edits. The artifact is useful evidence, not a proof of root cause or an editing boundary. It does not cover arbitrary runtime dependencies or every language. See [implementation discovery](localization-evidence.md) for bounds and evidence semantics.

Execute prefers exact `replaceText` edits. Malformed patches report hunk positions/counts; one bounded correction is allowed when source is unchanged. Stale source requires a refresh, and forbidden edits remain rejected. Proposal execution reserves a correction, phase completion and downstream Review before exploring. New current source ranges/definitions/graph relations establish progress; repeated queries, cached ranges and metadata changes do not. At the reserve boundary, the phase submits an evidence-backed edit or an explicit evidence/scope response. Host logs record request admission and budget shortfalls.

Review receives current source, full-file hashes/revision, public protection rules, cumulative base diff, recent Repair answers and public test evidence. Initial collection prefers complete small files and shared graph navigation of implementation helpers, bounded by six source reads and 48 KiB. Partial ranges explicitly leave unobserved code unknown. Review has no tools. Suggestions never block; a blocking defect needs a concrete scenario, expected/actual behavior or failure derivation, a relationship to the Issue/public API/regression, and a linked current source quote. Quote provenance alone does not establish a behavioral defect. Host finding IDs survive revision changes; omission does not close an open finding. Missing support becomes `EVIDENCE_GAP`, not a speculative Repair instruction.

Review records task scope independently of defect severity. `ISSUE_UNRESOLVED` and evidenced `PATCH_REGRESSION` can block; an unrelated defect shown to exist in baseline is `DEFERRED` for later work. Baseline/current source or public behavior comparisons support regression and deferral. The reported Issue itself remains blocking even though it also exists in baseline. Suggestions never block, and unresolved legacy findings require explicit resolution. Host `blocking` and `blockingReason` fields explain each decision; only confirmed blocking defects enter Repair.

Normal Review retains configured high thinking. A `LENGTH` response is discarded even when its JSON parses. One fresh compact semantic recovery uses the same model, low thinking and configured output cap. Nonempty malformed answers receive a context-free, no-thinking format conversion. Both share two persisted recovery credits across the workflow, with at most one recovery per decision. Recovery retains whole current evidence, counterevidence and unfinished finding records; it does not concatenate partial answers. Requests reserve decision/recovery steps and estimated input/configured output, and record unmet budgets before dispatch. Other stages retain their existing recovery policy.

`NEEDS_EVIDENCE` permits at most two host supplement rounds in the entire workflow, up to three requests per round, sharing eight source reads, 1 MiB originals and 32 KiB excerpts. Baseline and graph metadata reads share this allowance. Host caches validate hashes, separate base/current identity and expire current entries on revision changes; hits do not consume another physical read. Consumption is reserved before work and retained after Repair/recovery. The shared navigator can resolve public filenames and implementation helpers; unresolved names remain explicit gaps. Context pruning retains complete JSON records and current counterevidence.

These two rounds also cover probe feedback and correction. Source/probe failures return explicit diagnostics to Review even without successful observations. A failed logical probe may be corrected once across the workflow using its host ID; script versions and quota consumption survive recovery. Repeated failures, cached ranges and metadata changes do not establish new progress. The same corrected script runs on baseline and candidate; successful probes cannot be silently rewritten. Public scripts use `assertBehavior(ok, expected, actual)` to assert correct task behavior. Only complete structured assertions establish a behavioral observation; an exit code alone, unhandled script error or absent assertion does not. Review validates expectations and reconciles counterevidence before directing Repair.

Optional `probeRequests` link a finding to a public TS/JS entrypoint, reproduction code, expected observation and task basis. The host captures a bounded static import closure in one read-only operation, transpiles public modules and executes the same script against base/candidate using a pinned local dependency image. The script accesses the entrypoint exports through `entry`; relative imports use an immutable in-memory overlay. Dynamic imports, aliases, ESM-only dependencies or unavailable dependencies can require more evidence; they never trigger installation or silently substitute a claimed failure. No private evaluator or reference patch is supplied. Containers have a read-only root, separate scratch, no network/credentials, one CPU, 512 MiB and a 30-second deadline. Scripts are limited to 16 KiB; at most two scripts/six executions are allowed across the workflow. Each source closure is bounded to 256 modules, 6 MiB raw text and the existing global tool/time budget. Cached observations require matching source hashes, compiler, script and dependency-image identity. Repair can invalidate candidate observations while retaining the immutable base result. Logs record statuses, revisions and script/source hashes. Timeouts, missing dependencies and unavailable executions remain evidence gaps. Results return to independent Review; neither a passed reproduction nor independent patch acceptance auto-approves a patch. A passing counterexample must be explicitly reconciled before its finding can drive Repair.

Repair is a tool-calling Agent sharing Execute's runtime. Stable requirements, host finding IDs and failure diagnostics survive mutations; old source snippets/SHA do not. Test Repair prioritizes diagnostic file/line over the first diff hunk. `finishPhase` optionally returns `findingResponses` with an outcome, explanation and up to four citations per finding. Old overall outcomes/finding IDs remain readable. The host validates current public quotes/SHA, unknown or duplicate IDs and unanswered items, within the remaining read/tool budget. Only independently confirmed blocking defects are handed to Review Repair. No-edit answers still go through Test and independent Review; one answer cannot hide another unresolved finding or a failed Test. `LENGTH` discards all partial actions, with no concatenation/continuation. One compact recovery can refresh two current source ranges and expose only `replaceText`/`finishPhase`; it shares the existing edit-format correction credit, persisted across recovery. Input/configured output/downstream reserves gate admission; insufficient budgets preserve the candidate and unfinished tasks with a stop reason.

Repository tests, independent Issue acceptance, integrity checks and model Review are distinct evidence. A passed test suite or a valid proposal alone is not a successful Issue repair. See [validation](validation-v2.md) for measured limits and [model configuration](stage-models.md) for stage bindings.

The original Issue is the task authority; the Plan is a repair interpretation and cannot add acceptance requirements. Optional host feedback separates missing source, missing behavioral support, unresolved task scope and malformed requests. An invalid `taskQuote` names the finding and field, explains a mismatch or Plan-source confusion and returns the original task separately. Review must reassess scope; this correction consumes the same two feedback rounds without automatically rereading source, approving the candidate or declaring the extra scenario unrelated. Repeated references and arguments do not establish progress. Exhaustion leaves a specific unresolved reason.

Open findings retain host source records, public observations and Repair responses across re-review/restart. Current file SHA is checked again before a prior range is reused; unchanged cached originals can be rebound to the new workspace revision. Physical verification reads consume the existing shared source allowance, reserved before dispatch. Changed or unverifiable source cannot establish a current citation. Finding IDs and authoritative task requirements survive source invalidation. Baseline records require the same immutable base identity and verified full cache. No new feedback or correction credits are created by restoration.

The first `probeId` supplied by a model is an optional client label. The host assigns a formal ID and persists the alias/finding association; subsequent corrections must refer to that same host request. Cross-finding aliases and unknown prior host IDs are rejected. For example, `assertBehavior(entry.value === 2, 'value=2', String(entry.value))` supplies a boolean and two strings. Parameter errors report the exact argument and a usable example; the host never coerces values, flips assertions or edits expectations. Corrected scripts run on both versions and retain the one-correction/two-request/six-execution limits.

New tasks default to 25 minutes, retaining shorter explicit limits and saved deadlines. Normal Review has a 240-second request deadline, recovery 210 seconds, and finalization 30 seconds. Request/recovery/finalization time is reserved before Review; host evidence work reserves its deadline and the following judgment. Execute/Repair close exploration before spending that downstream reserve. Insufficient time records remaining/required/missing time with `requestIssued=false`. Timeouts remain incomplete judgments. A fresh bounded finalization signal saves the current candidate and pending findings without settling unknown request usage. See [convergence validation](review-convergence-20261006.md).
